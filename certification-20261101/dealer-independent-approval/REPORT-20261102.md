# Dealer approval must be independent per account (2026-11-02)

Nothing committed, pushed or deployed. Hosted database access was read-only SELECTs (project `ubvgixwhfybbyjuvxboj`). No migration was added or run.

## Path traced, hop by hop
| Hop | Finding |
|---|---|
| Table action (`AdminUsers.jsx`) | Approve is per row; matched rows with `x._id === u._id` |
| Client request | `POST /admin/users/:id/approve-dealer` with the row's id |
| Route (`adminRoutes.js`) | `adminOrSuper` + `requireDecisionAuthority` + `validateObjectId`; loads **one** user by `:id` |
| Service (`dealerApproval.service.js`) | Reads dealer/verification `WHERE user = id`; single-flight per id; calls the RPC once with `p_user = id` |
| Database function (hosted definition read) | Every statement is scoped to `p_user`/that user's dealer row; no other row is written |
| Hosted triggers on users/dealers/dealer_verifications | Only `updated_at` and a profile-sync-on-insert; nothing cascades between accounts |
| Hosted constraints | Unique index on `dealers."user"` and `dealer_verifications."user"`; status lives on each `users` row. The schema is already per-account, **so no new status model or migration is needed** |
| List response | **Defect found here** |

## Root cause (reproduced)
`GET /api/admin/users` reads rows with `.lean()`, which returns the database column `id` and **no `_id`** (probe: selected `id,name,...`, resulting `_id` values `[undefined, undefined]`). Every admin screen addresses rows by `_id`, so for all rows `_id` was `undefined`: the row key, the "busy" marker and the post-success update `x._id === u._id` (`undefined === undefined`) were shared by every row. One approval therefore updated every row's state in the table, and a request built from `u._id` carried no usable account id. The earlier backend tests did not catch it because their User mock returned `_id`, which the real model does not.

What I could not reproduce: your exact production click. The hosted database currently has two pending dealers (each with its own `users.status = pending`) and zero rows in `dealers`/`dealer_verifications`, so an approval there is refused (`DEALER_PROFILE_MISSING`) by design; I did not change any data. The reproduced mechanism explains "two rows change together" at the UI/identity layer; the server write path is per-account.

A second hazard found on the way: `db.updateMany` skipped `undefined` filter values, so `updateMany(t, {id: undefined}, ...)` would have updated **every row**. No current caller does this, but it is the kind of bulk write the brief prohibits, so it now throws.

## Fixes
- `backend/routes/adminRoutes.js`: every listed account carries `id` and `_id` from the same authoritative id.
- `src/api/api.exports.ts`: `withRowIds` normalises list payloads; `adminAPI.users` uses it (covers User Management, Seller Management and the command centre).
- `src/pages/admin/AdminUsers.jsx`: approve/ban match by exact non-empty id; an id-less row is refused with an error; after success only that row changes, then the list and counts are re-read from the server; failures leave the row pending and show the server's message.
- `backend/db/index.js`: `updateMany` refuses undefined filter values.
