# KAYAD Clean Deployment Alignment Audit — 2026-10-02

## Foundation audited

Input: the supplied `KAYAD-main (20)(1).zip`.

This archive was treated as the current source of truth. No external codebase was substituted.

## Findings

### 1. Application deployment is not the cause of the current custom-domain 404

The repository's production deployment contract is coherent:

- Vite production build
- `dist` output
- `npm ci`
- pinned Vercel CLI `60.1.3`
- Node `22.22.2` in CI/local certification
- explicit Vercel project targeting
- prebuilt production deployment
- release identity verification

The live Vercel project had a `Ready / Production` deployment. The observed `kayad.space -> www.kayad.space -> 404` pattern is therefore a domain/DNS routing problem, not evidence that the frontend build is missing.

### 2. Local Vercel state was incorrectly suitable for accidental source tracking

The supplied archive contained `.vercel/project.json`.

That file is machine-generated by `vercel link` and is not part of the application source. The clean foundation removes it and adds `.vercel/` to `.gitignore`.

If an existing Git checkout already tracks `.vercel`, remove it from Git tracking once:

```cmd
git rm -r --cached .vercel
```

This does not remove the local Vercel project or deployment.

### 3. The root deployment guide contained an obsolete production path

`DEPLOYMENT_GUIDE.md` documented:

```text
vercel --prod
vercel --prod --yes
```

This was replaced with the same pinned, explicit path used by the hardened CI workflow:

```text
vercel link
vercel pull --environment=production
vercel build --prod
vercel deploy --prebuilt --prod
```

The cleanup prevents accidentally deploying the wrong linked project or mixing preview and production state.

### 4. Canonical public hostname was inconsistent

Vercel was presenting `www.kayad.space` as the production hostname while application defaults, SEO URLs, sitemap URLs, and deployment verification were primarily using the apex `kayad.space`.

The cleaned foundation standardizes the browser-facing canonical hostname on:

```text
https://www.kayad.space
```

The API remains:

```text
https://api.kayad.space
```

The apex domain can continue redirecting to `www`.

### 5. Duplicate auction countdown implementation remained

The canonical countdown component existed at:

```text
src/components/CountdownDisplay.tsx
```

but an older duplicate remained at:

```text
src/components/features/auction/CountdownDisplay.tsx
```

The feature barrel had already been changed to re-export the canonical component, making the duplicate dead code. The duplicate has now been removed.

### 6. Stale documentation referenced a nonexistent validation script

`docs/VERCEL_DEPLOYMENT_HARDENING.md` referenced `npm run verify:vercel`, but the current package scripts expose `validate:vercel-ci`.

The documentation has been aligned with the actual package contract.

## What was deliberately NOT changed

- Auction lifecycle/rules
- Escrow authority/state machine
- Payment or transaction behavior
- Marketplace business logic
- Supabase migrations
- Backend provider configuration
- Vercel project identity
- Existing production deployment
- DNS records

Those areas were not changed merely to address the deployment incident.

## Required external fix

The repository cannot fix the current `www.kayad.space` DNS routing problem.

Use:

```cmd
vercel domains verify kayad.space --project kayad-space --scope themugos-projects
vercel domains verify www.kayad.space --project kayad-space --scope themugos-projects
```

Vercel's current CLI can diagnose the exact DNS configuration and recommended records. Apply only the records it reports at the external DNS provider, or delegate the domain to Vercel nameservers.

## Release gate

After the DNS fix, verify:

```cmd
nslookup -type=NS kayad.space
nslookup -type=CNAME www.kayad.space
curl -I https://www.kayad.space
```

Then run:

```cmd
set DEPLOYMENT_URL=<READY-PRODUCTION-DEPLOYMENT-URL>
set PUBLIC_URL=https://www.kayad.space
set API_URL=https://api.kayad.space
npm run verify:production
```

No application redeployment is required solely because the custom domain is misconfigured.
