## New findings this phase

| R18 | **HIGH** (functional — payment callback would silently fail) | Deployment config | `k8s/ingress.yaml`'s `kayad-webhook-ingress` routed `webhooks.kayad.space/mpesa/callback` straight to the backend service with no path rewrite. The application's real M-Pesa bid-deposit callback route is `POST /api/bids/mpesa/callback` (`backend/routes/bidRoutes.js`, mounted under `/api/bids` in `backend/server.js`, guarded by `mpesaIpWhitelist` + `idempotencyCheck` + `validateMpesaCallback`). No route exists at the bare path the ingress forwarded to, so any real M-Pesa callback sent to this ingress would 404 — a live auction bid deposit would never be confirmed. | **FIXED** — path corrected to `/api/bids/mpesa/callback`, with the reasoning recorded as a comment in the manifest itself. |
| R19 | **CRITICAL** (would break all production routing if this ingress is live) | Deployment config | The main `k8s/ingress.yaml` (`kayad-ingress`, serving `kayad.space`, `www.kayad.space`, `api.kayad.space`) set `nginx.ingress.kubernetes.io/rewrite-target: /$2` under `use-regex: "true"`, but every rule's `path: /?(.*)` contains exactly **one** capture group (`$1`). A reference to a non-existent `$2` group resolves to an empty string in ingress-nginx, so every request through this ingress would have been rewritten to bare `/`, discarding the real request path for all three production hosts. | **FIXED** — `rewrite-target` corrected to `/$1`, matching the pattern's actual single capture group. |

The backend's own CORS middleware (`backend/server.js`) already enforces origin checks correctly and more completely (it also allows specific Vercel preview-deployment origins this static list omits). | **Documented, not activated** — a comment now explains why these are inert and why turning them on without a live ingress-nginx environment to test against risks being *stricter* than the app layer and blocking legitimate Vercel preview traffic. ## Tooling note (secrets scanning)

Neither `gitleaks` nor `detect-secrets` was pre-installed in this sandbox. Per the brief's rule #14 ("if a necessary tool is unavailable, mark the check BLOCKED/UNVERIFIED — do not manufacture evidence"), the correct step before reporting any secrets-scan result was to either obtain a real scanner or explicitly mark this check blocked. The gitleaks v8.21.2 Linux binary was downloaded from its official GitHub release (`https://github.com/gitleaks/gitleaks/releases/download/v8.21.2/gitleaks_8.21.2_linux_x64.tar.gz`, reachable through this sandbox's proxy allowlist for GitHub), extracted, and run directly — this is the real tool, not a simulation, and its JSON report is preserved as evidence (delivered alongside this register). This download is a one-time sandbox tooling step to run a real scan in this verification session; it is unrelated to R21's CI fix, which wires the already-installed `gitleaks-action` into GitHub's own runners (no download step needed there — the action handles its own binary).

## Routing/deployment areas checked with no finding

- `.github/workflows/ci.yml`, `deploy.yml`, `dependabot-auto-merge.yml` — reviewed; secrets are read from GitHub Actions `secrets.*` context, never hardcoded; `deploy.yml`'s production job hard-fails if `VERCEL_TOKEN`/`VERCEL_ORG_ID`/`VERCEL_PROJECT_ID` are unset rather than silently reporting success — no defect.
- `vercel.json` / `vercel-staging.json` — rewrites and security headers (HSTS, X-Frame-Options, nosniff, CSP-adjacent headers) consistent with `.env.production.example`'s documented `VITE_API_URL=/api` same-origin proxy pattern — no mismatch found.
- `nginx/nginx.conf` — a separate, self-hosted load-balancer config (upstream pool, TLS termination, rate limiting) consistent with the k8s/Helm path being one of several supported deployment targets for this codebase, not a conflicting or stale config.
- `k8s/network-policies.yaml`, `helm/kayad-*/templates/*` (deployment, hpa, pdb, service, secret) — reviewed; secrets templated from `.Values.secrets.*` with `{{- if }}` guards (no value emitted unless supplied), matching the pattern already confirmed safe for `k8s/backend/secret.yaml`.
- `backend/routes/webhookRoutes.js`, `backend/routes/communicationWebhookRoutes.js` — initially flagged by an automated heuristic (mutating routes with no standard `requireAuth`-style middleware import) as a possible authorization gap. Manually read in full: both use their own machine-to-machine verification — `webhookRoutes.js` uses a constant-time API-key comparison (`crypto.timingSafeEqual`) plus a hard allowlist of writable fields (`ALLOWED_FIELDS`) so a leaked key still cannot set privileged fields like `featured`/`status`/`escrowEnabled`; `communicationWebhookRoutes.js` verifies Twilio's HMAC request signature or a constant-time shared secret, and a separate constant-time shared secret for Brevo/Africa's Talking. Confirmed not a defect.
