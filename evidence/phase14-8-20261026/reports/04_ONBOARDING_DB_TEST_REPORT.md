# Phase 14.8 - Database-backed dealer lifecycle (real local DB, real backend)
Scripts: `runbooks/phase14-8-20261026/localdb/e2e_dealer_lifecycle.cjs` (50/50, `logs/db-e2e-dealer-lifecycle.txt`) and `e2e_inventory_team.cjs` (60/60, `logs/db-e2e-inventory-team.txt`).
Covered: registration + validation, duplicate and concurrent-uniqueness, password hashing/no secrets in responses, email verification (token fixture set directly in the DB) and resend limits, login/session/CSRF, onboarding validation (400 writes nothing) and pending state, approval/rejection/suspension/reinstatement, dashboard access by state (dashboard readable so onboarding state shows; inventory writes refused until approved), approved dealer cannot rewrite payment details (409), team roles/org isolation/revocation, stale-session (token version, banned, forged token) rejection.
Proven: registration != approval; approval does not publish inventory (seeded pending listing absent from public search after approval); private-seller approval creates no dealer identity and cannot enter dealer verification.
Test-technique notes: cars are seeded by SQL with triggers bypassed (disposable DB only); the owner account is made by setting the owner email; listing quota uses a fixture subscription row. Listing creation via API requires a photo -> 400 verified; actual photo upload needs Cloudinary: **not executed**. Default rate limits were relaxed for the harness (429s were observed earlier at default limits for registration/verification).
