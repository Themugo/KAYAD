# 04 — Team invitation and acceptance audit
Method: new real-backend journey `ci/db-journeys/17_team_invitation_lifecycle.mjs` (39 checks) against a disposable database. The backend builds the real invitation e-mail; a loopback provider stub (`brevo_stub.cjs`, preloaded via NODE_OPTIONS, no production-code change) records it, the journey extracts the e-mailed link token and uses exactly that token. **No token is injected into the DB** (the earlier journeys 12/16 did inject one, so the true link path had never been exercised).
Result: 39/39 PASS: create (new, unregistered invitee), only SHA-256 stored, link = `FRONTEND_URL/dealer/setup?invite=<64 hex>`, 7-day expiry, duplicate 409, bad role 400, self-invite 400, audit event; provider failure → 201 with `email.sent=false` + reason, resend delivers, resend invalidates the previous token; signed-out 401, wrong email 403 (stays pending), other dealer's owner 403, new user accepts → membership active with correct dealer/member/role, token cleared, audit event, duplicate acceptance 404, `/my-workspace` shows it, persists after re-login, owner roster shows it, other dealer's roster does not; expired 410, revoked 404 then re-issue works, existing member 409, role change effective next request, cross-dealer change/remove/resend 404, member cannot invite 403, removal cuts access on the next request.
**I could not reproduce a backend failure of "recipient agrees but is not added".** Defects actually found and fixed:
1. The invitation e-mail named the inviting person, not the dealership (A6 failed) → now `dealerPublicName(dealer)` for invite and resend.
2. After accepting, the cached "no dealership" answer (`useMyDealership`) was not cleared and the success page sent the member to `/`, not their workspace → cache reset and link to `/?nav=dealership-workspace`.
Not fixed / likely friction (NOT TESTED in a browser): a brand-new invitee who must register and verify e-mail may lose the `?invite=` return path through sign-up/verification and has to re-open the e-mailed link; acceptance is a single guarded update backed by DB unique indexes (`dealer_teams_dealer_member_uq`, token-hash unique) but a concurrent double-accept would surface as a 500, not a clean 409. A dealer-role or staff account cannot join (by design: members join with a personal account).
E-mail provider: delivery to a real provider is **BLOCKED/NOT VERIFIED** (no credentials); only the stub was exercised.
