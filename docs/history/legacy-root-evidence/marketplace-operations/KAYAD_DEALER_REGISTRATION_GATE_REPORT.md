# KAYAD Dealer Registration & Auth Convergence — Gate Report (Phase 2)

Method: full code-level trace of the dealer registration path, frontend entry through backend persistence, reading the actual route/controller/middleware bodies rather than inferring from names. End-to-end browser proof (the brief's own warning: "do not declare registration complete merely because the first API call returns HTTP 200") is Phase 11's job with real tooling (Playwright); this phase establishes that each step is genuinely wired and correctly server-enforced at the code level, which is the prerequisite for that later E2E pass to mean anything.

## Correction carried in from this phase's own work

Phase 0's ownership map treated `dealerAPI` (`src/api/api.exports.ts`) as backing only the dead legacy dashboard subtree. **That is incomplete.** `dealerAPI.getOnboarding()` / `dealerAPI.completeOnboarding()` are used by the canonical, live `DealerOnboarding.jsx` (routed at `/dealer/onboarding`) and correctly hit `GET/PUT /api/dealer/onboarding` — which are declared *before* `dealerRoutes.js`'s router-level `protect, dealerOnly, requireApproved` guard, with their own explicit `protect, allowRoles("dealer")` (intentional: a newly-registered, not-yet-approved dealer must still reach onboarding). Only `dealerAPI`'s *other* methods (`.analytics`, `.getSettlement`, `.team*`, etc.) are dead-frontend-only. `dealerAPI` is a mixed-use object, not a uniformly dead one — noted here rather than rewriting Phase 0's document.

## Gate verdict

`DEALER_REGISTRATION_GATE`: **PASS WITH ONE OPEN ITEM (R1-NEW)**, not `BLOCKED`. Every step from entry through dashboard access is genuinely implemented and server-enforced at the code level — no step is a UI-only illusion, no client-supplied flag is trusted for anything load-bearing (role, onboarding completeness, or approval), and two previously-real defects (the timing oracle, the half-created-account race) are already fixed with evidence in-code. The one open item — unapproved dealers reaching dashboard read-endpoints before admin sign-off — is real but, per the Phase 2 severity assessment in the gap register, does not cross a tenant boundary or bypass the one financially-relevant control (listing creation, which has its own separate, correctly-enforced progressive-verification gate). It is carried into Phase 5 rather than blocking this gate, consistent with the brief's own distinction between a release-blocking defect and a scoped follow-up.

This phase did not execute the flow against a running server/browser (no live Supabase project is provisioned in this sandbox — the same limitation `src/services/authApi.ts`'s own header comment discloses); the trace above is a direct code read, which is the correct evidence standard for this phase. Phase 11 is where this becomes a Playwright-executed, running-server claim.
