# KAYAD Dealer Platform — Security, Verification & RLS Report (Phases 4–5)

All findings below are either a direct source-code read or an empirically-run, read-only query against the live, connected Supabase project ("KAYAD EA", `ubvgixwhfybbyjuvxboj`, ACTIVE_HEALTHY) via `mcp__Supabase__execute_sql`/`get_advisors`. No write, migration, or destructive statement was executed against that project at any point in this phase.

## Phase 4 — Verification & sensitive-data handling

**Document model, as it actually exists (not as the brief's wording assumes):** dealer "documents" in this codebase are structured identity *fields* (government ID type + number, KRA PIN, optional business registration number), submitted as JSON inside `dealer_verifications.documents`, not scanned image/PDF *files*. No multer/upload middleware, signed-URL issuance, or malware-scanning code path exists for this flow — because there is nothing to upload. This is a scope correction against the brief's Phase 4 wording (which anticipates file uploads), not a defect: the upload-security checklist items (content-type/size validation, malware scanning, version history) don't apply to a feature that doesn't exist. If the product intent is actually to collect scanned ID/KRA documents as files, that is an unbuilt capability, flagged here for the user's product decision rather than assumed.

**Self-approval / peer-approval:** confirmed not possible. Every write to `dealer_verifications.verification_status` goes through either the `kayad_apply_dealer_verification_atomic` SQL RPC (`REVOKE ALL ... FROM PUBLIC`) or `transitionDealerVerification` behind `/api/verification/admin/*`, itself behind `protect` + `allowRoles("admin","superadmin")` (`verificationRoutes.js:1-31,83-86`). No dealer-facing endpoint can set `verification_status`. Empirically reconfirmed: `authenticated`/`anon` Postgres roles hold no `UPDATE` grant on `dealer_verifications` at all (§RLS below), so even a direct PostgREST call with a dealer's own JWT cannot write this column regardless of what the RLS policy text says.

**Admin decision integrity:** `reviewedAt`/`reviewedBy` are set server-side from `actorId`/`now()`, never client-supplied (`dealerVerificationService.js:119-128`, the RPC equivalent). `transitionDealerVerification`'s own `allowed` state-transition map (`pending→{approved,rejected,suspended}`, `rejected→{pending}`, `approved→{suspended}`, `suspended→{approved}`) rejects an invalid transition with a 409 before any write — e.g. you cannot jump `rejected→approved` directly, which is a sensible, deliberate guard, not a gap.

**Cross-dealer document access:** `getVerificationStatus` scopes to `req.user.id`; `getVerificationById` takes a verification-record UUID but is gated to `admin`/`superadmin` only — no dealer-facing endpoint accepts another dealer's ID to fetch verification data. No cross-dealer leak found in this area.

**Masking:** `maskPhone()` is applied to the OTP-request response (`verificationController.js:47`); `maskAccountNumber()` exists and is applied in the one admin payout-account context checked (`adminRoutes.js:2184-2195`). The dealer's own KRA PIN/ID number is returned unmasked only to that same dealer (their own data, appropriate) and to admin reviewers (the authorized review workflow, appropriate). No endpoint was found returning another dealer's or a public viewer's unmasked sensitive identity/payment fields — `GET /dealer-platform/profile/:dealerId` (public, unauthenticated by design) was checked directly and returns only business name, bio, location, approval flag, member-since, and aggregate stats; no payment or ID data (`dealerPlatformController.js:105-122`).

**Two confirmed CRITICAL, live-database defects found while tracing this area are in the gap register, not restated in full here: R12 (onboarding completion broken — missing `dealers` columns) and R14 (dealer suspend broken — `verification_status` CHECK constraint missing `'suspended'`, a second write path R13's earlier analysis missed).**

## Phase 5 — Authorization, RLS, cross-tenant isolation

**Critical RLS column-mutation investigation (the brief's specific ask):** full method and result in the gap register's R11. Summary: the `dealer_verifications` owner-scoped `UPDATE` policy is row-only (not column-restricted) exactly as the brief warns is a common blind spot — but empirically, `authenticated`/`anon` have **no base `UPDATE`/`INSERT`/`SELECT`/`DELETE` grant on this table at all** (confirmed via `information_schema.table_privileges` against the live project), so the gap in the policy text is not reachable by any client-side code path. The same no-grant pattern was confirmed for `dealers`, `dealer_teams`, `leads`, and `marketing_campaigns`; a project-wide sweep found exactly one non-`service_role` data grant anywhere in the public schema (`authenticated: SELECT` on `vehicle_valuations`). Verdict: **the structural weakness exists in the policy definitions but is not currently exploitable**, because every actual read/write already goes through the Express backend's `service_role` connection, where the authorization logic audited in Phases 0-4 is the real boundary. Recorded as a hardening recommendation (tighten the policy anyway, so a future change to the grant posture doesn't silently reopen this), not a live defect.

**Dealer organization & team authorization:** `dealer-platform`'s `/team/*` routes use `protect, dealerOrgAccess(<permission>)` (e.g. `canManageTeam`), scoping by organization membership rather than raw role — not independently re-derived in this phase beyond what Phase 0/1 already confirmed; a full read of `dealerOrgAccess`'s implementation (does it correctly verify org membership from a DB row, not a client-supplied org ID) is a carry-forward item, not yet done.

**Cross-tenant isolation, application layer:** reconfirmed from Phase 1's wiring matrix — every dealer-platform controller read in this engagement filters by `req.user.id`/`dealer: dealerId` server-side (leads, customers, auctions, inspections, analytics, marketing, finance). No endpoint was found accepting a client-supplied dealer/org ID for these without an ownership check, except the explicitly-public, explicitly-non-sensitive `/profile/:dealerId` storefront view.

**Cross-tenant isolation, database layer:** `cars`, `escrows`, and `users` carry **zero** privilege grants of any kind to `authenticated`/`anon` (not even `REFERENCES`) — fully inaccessible outside the backend's `service_role` connection. This is a strong, deliberate, project-wide isolation posture, not something assembled piecemeal for the dealer feature alone.
