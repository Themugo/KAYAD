## R11 — Critical RLS column-mutation investigation (Phase 5 item, run early because live DB access was available)

The brief explicitly warns: "Do not assume that a policy restricting rows also restricts the columns within those rows." `dealer_verifications`'s `UPDATE` policy (`dealer_verification_owner_update: USING (auth.uid() = "user") WITH CHECK (auth.uid() = "user")`) is exactly this pattern — row-scoped, not column-scoped — and the table holds both dealer-editable fields (`documents`) and admin-only fields in the same row (`verification_status`, `rejection_reason`, `reviewed_by`, `admin_notes`, `suspension_reason`, `suspension_expires_at`, `otp_hash`, `otp_attempts`). On the policy alone, a dealer could self-approve by setting `verification_status='approved'` on their own row.

**This was tested empirically against the live, connected Supabase project ("KAYAD EA", `ubvgixwhfybbyjuvxboj`, ACTIVE_HEALTHY) via `mcp__Supabase__execute_sql`, read-only queries only — no writes, no migrations, nothing destructive.**

Finding: `information_schema.table_privileges` shows the `authenticated` and `anon` Postgres roles hold **only `REFERENCES`/`TRIGGER`/`TRUNCATE`** on `dealer_verifications`, `dealers`, `dealer_teams`, `leads`, and `marketing_campaigns` — **no `SELECT`, `INSERT`, `UPDATE`, or `DELETE` grant at all**. Only `service_role` (used exclusively by the Express backend, never exposed to a browser) has those. A project-wide scan confirms this is the deliberate, consistent pattern: across every table in `public`, the only non-`service_role` data-access grant anywhere is `authenticated: SELECT` on `vehicle_valuations`. Postgres checks the base `GRANT` before RLS policies are even consulted, so **the row-level `WITH CHECK` gap is real on paper but not reachable**: there is no code path (direct PostgREST call with a dealer's own JWT, or otherwise) by which a dealer can issue an `UPDATE` against this table at all — every write genuinely goes through the Express backend's own authorization chain (the `protect`/`dealerOnly`/`requireApproved`/`requireDealerVerification` middlewares already audited in Phases 0-2, and the `kayad_apply_dealer_verification_atomic` SECURITY DEFINER RPC for admin decisions, itself `REVOKE ALL FROM PUBLIC`).

**Verdict: the structural RLS gap the brief's warning anticipates is present in the policy text but not exploitable, because of a second, independent control (schema-level privilege grants) that fully closes it.** This is recorded as **LOW** severity / **informational hardening recommendation**, not a live defect: the policy should still be tightened (e.g. `WITH CHECK` restricted to non-privileged columns via a trigger, or the grant posture made the documented, intentional control with a comment, since right now the safety is incidental rather than defense-in-depth-by-design) so that a future change which *does* grant `authenticated` direct table access doesn't silently reopen this. Recommendation only — not implemented in this phase, since it is not a current defect requiring urgent repair.

**Cross-tenant isolation (same live-DB method):** the identical grant check was run against `cars`, `escrows`, and `users` — none appear in the `authenticated`/`anon` privilege list at all (not even `REFERENCES`), meaning they are completely inaccessible to any non-`service_role` connection. Combined with Phase 1's confirmation that every dealer-platform controller filters by `req.user.id`/`dealer: dealerId`, there is no cross-tenant read/write path found via either the application layer or direct DB access for the tables checked. A full per-table sweep (every table named in the brief's Phase 5 list — documents, listings, team, subscriptions) is still owed as a complete Phase 5 deliverable; this entry covers the specific tables this phase's investigation reached.

## R14 (new, Phase 4) — Dealer suspend/reinstate endpoints are confirmed broken against the live database (CRITICAL)

There are **two independent admin-verification write paths** to `dealer_verifications`, not one:
1. `kayad_apply_dealer_verification_atomic` (SQL RPC, `20260909091703_dealer_commercial_payout_lifecycle.sql`) — only ever writes `'approved'`/`'rejected'`/`'pending'` to `verification_status` (confirmed its own `CASE` statement has no `'suspended'` branch). Reachable today only via `backend/routes/adminRoutes.js` (one `.rpc('kayad_apply_dealer_verification_atomic', ...)` call site).
2. **`backend/services/dealerVerificationService.js:transitionDealerVerification`**, reachable via the separate, fully-featured `/api/verification/*` API (`verificationRoutes.js`, properly `protect`ed + `allowRoles("admin","superadmin")`-gated) — `POST /api/verification/:id/suspend` and the `pending→suspended` transition both call `update("dealer_verifications", id, { verificationStatus: "suspended", ... })` directly. `VERIFICATION_STATUSES` (code-level) explicitly includes `"suspended"` as valid, but **the live table's CHECK constraint is `verification_status IN ('pending','approved','rejected')` only** (confirmed via `pg_get_constraintdef` against the connected Supabase project) — `'suspended'` is not in it.

**Effect: every call to the dealer-suspend admin action, and the `suspended→approved` reinstate transition on top of it, will fail with a live Postgres constraint-violation error.** This is a second, independently-confirmed release-blocking defect (alongside R12's onboarding-column gap), specifically breaking the brief's own Phase 8 requirement to "manage suspension/reinstatement properly." My Phase 3 analysis (R13, now struck through) initially concluded this class of concern didn't hold, based on the RPC path alone — that conclusion was incomplete because it missed this second write path; corrected here rather than left standing, per this engagement's self-correction discipline.

**Proposed fix (additive, matches the brief's migration rules), not yet applied — same authorization question as R12:**
```sql
ALTER TABLE dealer_verifications DROP CONSTRAINT dealer_verifications_verification_status_check;
ALTER TABLE dealer_verifications ADD CONSTRAINT dealer_verifications_verification_status_check
  CHECK (verification_status IN ('pending','approved','rejected','suspended'));
```
Purely additive to the allowed value set; does not alter existing data, column type, or any other constraint.

## R15 (Phase 6, resolved Phase 12) — Dealer could freeze bidding on their own live auction via an unvalidated `status` field

**Resolved in Phase 12 with a full read of the escrow/auction-to-car-status dependency graph** (`escrow.service.js`, `escrowStateMachine.js`, `auctionSettlement.service.js`, `auctionFulfilment.service.js`, `auctionClose.service.js`, `bidController.js`, `auctionController.js`), answering the question left open in Phase 6:

- **The feared broad gap is not real**: escrow release/payout logic (`escrow.service.js`, `escrowStateMachine.js`) never reads `car.status` to gate anything — it transitions purely on its own `escrow.status`. The auction settlement/fulfilment services only *write* `cars.status` as a downstream side-effect once the financial decision is already made from the escrow/auction's own state, never read it as an input. So a dealer flipping `status` between `available`/`sold`/`reserved`/`archived` cannot disrupt an escrow or auction's actual money movement.
- **But a narrower, real gap was found and fixed**: `car.status === "rejected"` IS read as a financial gate — `bidController.js`'s `placeBid` (409s any bid) and `auctionController.js`'s detail/bid-list routes (404) both stop accepting bids once `status` is `"rejected"`, by design, for admin-moderated listings (`adminRoutes.js`, `duplicateController.js` are the only intended writers). `updateCar`'s generic `allowedFields` loop included `status` with **no enum validation and no entry in the existing `AUCTION_LOCKED_FIELDS` guard** — so any dealer, editing their own listing through the ordinary edit endpoint, could set `status: "rejected"` on their own car at any time, including mid-auction, silently freezing all further bidding on it without going through the amendment/lock workflow `AUCTION_LOCKED_FIELDS` exists specifically to enforce for every other auction-sensitive field.
- `bulkUpdateListings`'s own `allowedStatuses` whitelist (`dealerPlatformController.js:224`) already excluded `"rejected"` — this path was never exposed.

**Fix applied** (`backend/controllers/carController.js`'s `updateCar`): a new guard blocks any non-staff caller from writing `status: "rejected"` (unless the car is already `"rejected"`, allowing idempotent resubmission), returning `403 STATUS_ADMIN_ONLY`. This is additive and narrowly scoped — every other status transition a dealer legitimately needs (`available`/`sold`/`reserved`/`archived`/`pending`/`draft`/`active`) is untouched. Verified: `node --check` (syntax), full backend `npm test` (1159 Jest + 16 vitest + 1 node:test, all passing, no regressions), full frontend `tsc --noEmit` + `vite build` (unaffected by this backend-only change, re-run as a sanity check anyway).

## R17 (new, Phase 12 — found while implementing the R3 fix, FIXED same phase) — Finance tab data contract exposed raw UUIDs instead of names

While wiring the Finance tab to `getFinanceApplications` (R3), direct inspection of the live table definition (`supabase/migrations/20260908043000_dealer_platform_domain_end_to_end.sql`) and the controller's query (`findAll("loan_applications", ...)`, a plain unjoined select) showed the response's `vehicle` and `applicant` fields are bare `uuid` foreign keys, not names — `findAll` performs no join. Had the Finance tab simply been bound to this response as the brief's R3 wiring fix implied, it would have rendered raw UUIDs (or silently blank/undefined, since the frontend code was written expecting fields like `vehicle.title`/`applicantName` that do not exist on the raw row) instead of a usable applicant name and vehicle title — a defect that would have shipped invisibly inside what looked like a complete fix.

**Fixed, not just documented:** `backend/controllers/dealerPlatformController.js#getFinanceApplications` now collects the distinct `vehicle`/`applicant` ids from the fetched applications and resolves them via batched `Car.find({ id: { $in: vehicleIds } })` / `User.find({ id: { $in: applicantIds } })` lookups (the identical pattern `getInspectionOrders` already uses to resolve vehicle titles for inspections), attaching `vehicle` (title string) and `applicantName` (string) onto each returned item. No schema change, no new table — purely an enrichment of the existing read path, scoped to the already-dealer-filtered rows (`filters: { dealer: req.user.id }` is unchanged), so this introduces no new cross-tenant exposure. Verified via the same full test/build/lint battery as R3 (`npm run lint`, `npm run build`, full `vitest run` 643/643, backend `npm test` 1159 Jest + 16 vitest + 1 node:test, all passing) plus a manual read of the resulting JSON shape against the updated frontend JSX.
